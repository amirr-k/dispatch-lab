# DispatchLab

**[dispatch-lab](https://amirr-k.github.io/dispatch-lab/)** — a real-time delivery-dispatch simulator: place an order, watch the backend assign a driver and route it with A*, then close a road and watch it reroute live. A comparison mode runs identical demand through a greedy baseline and a batch-optimized assignment algorithm and reports the measured difference.

The backend is a free-tier Render instance behind Neon Postgres, so the first request after a period of inactivity can take a few seconds to wake up.

## What's actually happening

Every visible thing in the app — driver positions, route lines, the event feed — is a rendering of state a Go backend computes and owns. The browser never simulates anything; it sends commands (`place_order`, `close_road`, `pause`) over REST and WebSocket and draws whatever events come back. That split is what makes two features possible that would otherwise be hard to trust:

- **Deterministic replay.** Simulations run on an internal virtual clock, never `time.Now()`, so the same seed and command sequence always produce the same event sequence. Every event is appended to a Postgres log with periodic snapshots, so a finished run gets a permanent `/replay/:id` URL that reconstructs and scrubs through its own history.
- **A fair algorithm comparison.** Because outcomes are reproducible from a seed, the compare page can run the exact same arrival sequence through a baseline (nearest-idle-driver) matcher and a batch min-cost matcher and report real differences in completed deliveries, pickup time, and distance — not two different random simulations that happen to look different.

Each active simulation runs in its own goroutine and owns its state exclusively; every external interaction is a command sent through a bounded channel rather than a lock, which is what lets `go test -race` stay clean. Matching narrows candidate drivers with a spatial grid before costing them out with A*, so it doesn't route every idle driver on every order. Design rationale, the WebSocket wire protocol, persistence/replay mechanics, and the security model for a public multi-tenant demo are written up in [docs/architecture.md](docs/architecture.md).

## Stack

- Go backend (REST + WebSocket), owns all simulation, routing, and matching state
- React, TypeScript, and Vite frontend
- PostgreSQL (Neon) for sessions, events, snapshots, and benchmark results, with an in-memory fallback for local development
- Render (backend) and GitHub Pages (frontend), auto-deployed on every push to `main` that passes CI

## Performance

Numbers are measured, not estimated — [benchmarks/results/latest.md](benchmarks/results/latest.md) is generated by `cmd/evidence`, which drives the matching, routing, and simulation packages directly and folds in `cmd/loadgen` output against a live server, rather than accepting a hand-typed claim. A few from the latest run:

- Recomputing routes after a road closure: p50 0.005ms in-process compute.
- Full round trip for a closure — HTTP in, simulation queue, affected-driver detection, A* recompute, event serialization, WebSocket out — measured end to end against a live server and real Postgres: p50 ~1ms, p95 ~2ms over 250 trials.
- Batch-optimized matching against 40 drivers / 20 orders: p50 ~1.3ms.

Reproduce it yourself: run the server, then `go run ./cmd/loadgen -mode=closure-latency -output=closure.json` against it, then `go run ./cmd/evidence -loadgen-closure-latency=closure.json`.

## Local development

Backend (Go 1.26+):

```
go run ./cmd/server
```

Runs on `:8080` by default. With no `DATABASE_URL` set it falls back to an in-memory store, so nothing else needs to be running. To use Postgres instead, set `DATABASE_URL` to a connection string; migrations apply automatically on startup. Other environment variables: `ADDR`, `ALLOWED_ORIGINS`, `LOG_LEVEL`, `LOG_FORMAT`, `RATE_LIMIT_PER_SECOND`, `RATE_LIMIT_BURST`.

Frontend (Node 22+):

```
cd apps/web
npm install
npm run dev
```

Defaults to talking to a backend at `http://localhost:8080`; override with `VITE_API_URL`.

## Tests

`go test ./...` for the backend (includes a `-race`-clean suite and property tests against a brute-force matching baseline and Dijkstra). `npm test` for frontend unit tests, `npm run test:e2e` (Playwright) for end-to-end and accessibility checks.
